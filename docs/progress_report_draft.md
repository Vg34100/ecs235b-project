# Progress Report Draft

## Analyzing Information Flow Violations in LLM Pipelines using Access Control Models

This project studies whether failures in large language model (LLM) pipelines can be described as information-flow violations rather than only as bad outputs. The current implementation models a pipeline run as a set of sources and policies: the user prompt, tool output, system policy, and attacker instruction are treated as distinct information sources, and outputs are checked against policies describing which sources are required and which are forbidden. To ground the project in a public benchmark, the implementation now uses `InjecAgent`, a prompt-injection benchmark for tool-integrated LLM agents, as the main dataset basis for the progress-report version.

The main technical progress so far is that the project has moved from a toy MVP to a benchmark-backed audit pipeline. Raw `InjecAgent` data is downloaded locally, converted into a project-specific internal schema, and processed through a trace-based evaluation pipeline. Each run now produces a stable trace object containing the case id, prompt, available sources, required sources, forbidden sources, model answer, reported source use, inferred source use from ablations, final merged source use, and final violation judgment. The current system also exports JSON, CSV, markdown trace tables, and a compact evaluation summary for later analysis and reporting.

The policy layer currently supports three violation types: `missing_required_source`, `forbidden_source_used`, and `consistency_violation`. The first flags runs where the answer appears not to rely on a required source such as `tool_response` or `system_policy`. The second flags runs where a forbidden source such as `attacker_instruction` appears to influence the answer. The third flags answers that appear to follow the attacker instruction even when the source list alone would not fully capture the problem. This gives the project a broader and more defensible policy model than the initial MVP, which only checked required and forbidden sources.

An initial real-model evaluation has been completed using `meta-llama/Llama-3.2-1B-Instruct` on a 30-case subset of processed `InjecAgent` cases. On this subset, the current system found 5 compliant cases and 25 violating cases. The dominant failure mode was `forbidden_source_used` with 19 occurrences, followed by `missing_required_source` with 12 occurrences, and `consistency_violation` with 6 occurrences. These counts overlap because a single run can trigger multiple policy violations. The most important early finding is that the main failure pattern is forbidden-source influence: in many cases, the model appears to incorporate or follow attacker-originated instructions that should remain non-authoritative. A second recurring pattern is incomplete use of required sources, especially omission of `system_policy` or `tool_response`.

These results are promising, but the main limitation is still attribution quality. The current detector merges two signals: self-reported source use from the model and ablation-based source inference. This works well enough to produce interpretable early results, but self-reported source use is still noisy, and small local instruct models sometimes return partial JSON or incomplete source lists. Because of this, current work has focused on conservative source merging, partial-JSON recovery, and trace exports that make failures easier to inspect. In other words, the core audit pipeline is functioning, but attribution remains the main technical challenge for the final project phase.

The next steps before the final submission are to expand evaluation on the curated benchmark subset, choose a small number of representative case studies, and improve the presentation of analysis artifacts. The strongest current claim is that the project has implemented an initial policy-based audit framework for benchmark-backed LLM pipeline traces and has already observed a clear pattern of forbidden-source influence in early experiments. The final stage of the project will focus on improving attribution robustness, expanding the evaluation set, and polishing the analysis and discussion.
